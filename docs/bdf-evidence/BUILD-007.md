## 1. Content revision, render generation and saved snapshot (engine)

**Before.** `Document` had one counter, `generation`, bumped by edits, undo, redo, saves, layer toggles and reading-colour changes (it exists to invalidate caches and to tell autosave what to write), and a `dirty` flag that undo and redo set to `true` unconditionally. So (1) nothing in the engine said "the content changed" apart from "something changed", which a client making a request against a document cannot use; and (2) undoing back to the content that is in the file left the document marked unsaved, because dirty was a history fact, not a content fact.

**Now** (`crates/engine/src/lib.rs`):

* `Document::content_revision()`: advances on every edit, undo, redo, revert and reload, and on nothing else. A save does not advance it (same content), nor does a display-only change (`set_hide_comments`, `set_reading_colors`, layers), nor a failed edit (rolled back before the bump). It never repeats within a session; `reload` keeps the document id, so it continues from the old value rather than restarting.
* `Document::edit_generation()` is unchanged and still the cache/autosave counter. The two are deliberately different numbers.
* **Content identity**: each editor state carries an id. Applying an edit gives the new state a fresh id and stores the previous id in the undo entry; undo and redo bring back the id the restored state had. `Document::content_id()` is the working content's id and `saved_content_id()` the id of the content last opened from or written to a file (`None` for content that has never been in a file: a combined or extracted document, a recovered one, or one whose rebase on the saved file was rejected). `dirty` is now derived from `saved != current` at every point that changes either, so **undoing back to the saved content is clean again**, redoing past it is unsaved again, and a different edit on the same base is never mistaken for the saved content (revision equality could not tell these apart).
* A save made while edits were in flight (`Saved::EditedSince`) leaves the saved identity alone: undoing back to the in-flight-saved content still reads as unsaved. That is the conservative direction (one needless prompt, never a false "clean") and is recorded rather than fixed.

Tests (engine, seven, all through the public session API): the revision moves with content and only with content (save and `set_hide_comments` leave it, the cache generation does move on save); a failed edit leaves revision and history alone; undo/redo/save round trips in both directions; two different edits on the same base are never "saved"; an overlapping save keeps the later edit and stays unsaved; new, recovered, reverted and reloaded documents keep the invariant; a rejected rebase leaves the saved-content test and `dirty` in agreement. **Mutations, each reverted after the run:** undo always dirty (fails `undoing_back_to_the_saved_content_is_clean_again`); a save that bumps the revision (fails the revision test); a rebase that does not record the saved content (fails 2); undo that does not advance the revision (fails 1); reload that restarts the revision (fails 1); a rejected rebase that leaves the old saved identity (fails 1).

## 2. The service

`crates/app-service`, modules `operations`, `results`, `errors`, `effects`, `version` and `service` (private); the README states the contract.

* **Operation descriptors** are the one table of what exists (stable id, summary, capability, access class, release status, needs-document, needs-revision). The service never depends on `automation::ToolDef`; adapters are meant to derive tool definitions and UI availability from the descriptors. A test builds one typed request per operation and checks it against its descriptor: whether a revision is carried, and that anything which changes content or writes a file carries one.
* **Typed requests, results and errors.** The mutation variants of `Operation` carry `expected_revision: u64` as a field, so a changing request cannot be built without naming the revision it was made against. `OperationResult` has the outcome, the document's `DocumentVersion` after it, warnings and committed effects. `OperationError` has a stable code from a closed set, a message, a retryable flag, a typed conflict (`StaleRevision`, `FileExists`, `FileChanged`, `FileGone`, `UnsavedChanges`) and a `committed` list that is empty for every failure that stops before an effect and names the write when the failure came after one.
* **`DocumentVersion`** keeps the three things apart: `content_revision`, `render_generation`, and the saved snapshot (`content` / `saved_content` ids, `dirty()` derived from them).
* **Private ownership.** `Service` holds the engine `Session` in a private field and exposes no `&mut Session` or `&mut Document`. `DocumentView` is the read-only facade (name, page count, version, info, next undo/redo labels). Every change passes `Service::execute`, whose order is fixed and each failure leaves bytes, history and files as they were: schema version, document, revision, arguments, then the operation.
* **Documents are `(session, number)`.** The session id is random per service (hasher keys and the clock); a key from another session is `not_found`, so a document number from another window or run cannot reach the wrong document.
* **Schema negotiation.** `SCHEMA_VERSION = 1`, `OLDEST_SCHEMA = 1`. A request outside the range is `unsupported_schema` with the supported range and which side must update, and it is checked before the document, even for a request that would also fail on its document. There is nothing to migrate yet.
* **Stale mutations.** A rotate, undo, redo, save or close made against any revision but the current one is `conflict(StaleRevision { expected, current })` and changes nothing: version, pages and history are compared before and after.
* **Saving in two halves**, so file I/O can run on a worker: `prepare_save(key, expected_revision, …)` (checks the revision, takes the bytes of that revision, decides what the target may replace), `PreparedSave::write()` (no reference to the service; replaces only what the plan allows, checked at the moment of replacement, through the platform persistence and confinement functions), `finish_save(plan, written)`. A late result for a document edited meanwhile keeps the edits and leaves it unsaved (`edited_since`); for a document closed meanwhile it leaves the file and touches nothing else; a worker can ask `is_current(key, revision)` first. A written file whose document could not be refreshed from it is `internal_failure` with the write in `committed` and a message saying the changes are still open and unsaved.
* **Files.** `Service::confined_to(root)` accepts only root-relative paths with no `..`, no drive and no root of their own, pins the destination folder (Windows) and revalidates it at the commit; opening checks the size against `MAX_OPEN_BYTES` (512 MiB, an interim admission limit) before reading. Messages name the file, never the folders above it (the one exception is the platform's own "the original is in …" for a lost original, which the user needs).

Tests (service, 19 through the public contract): descriptors; schema negotiation including the order; session-qualified keys; page numbering from 1; a stale mutation of every kind changes nothing; a request against the current revision is accepted and moves it forward; undo back to the opened content is clean and a save does not move the content revision; bad arguments (degrees, page 0, negative, past the end, `i64::MAX`, empty) refused before anything moves, not even the render generation; history; close refuses unsaved changes; a save writes the file and an independent new session reads the edit back; a changed file is refused with both versions intact and replaced only on a matching fingerprint (wrong and malformed ones refused); a deleted file is not silently recreated and a new path is not overwritten; a never-saved document needs a path; the split save checks the revision and its debug print never carries the document; a late save result keeps the newer edit; a save finishing after close leaves the file only; confined services refuse every escape and write below the root; a folder swapped for a junction out of the root is not written through (byte-identical decoy, so the version check cannot be what stops it). **Mutations, each reverted after the run:** no revision check (fails 2); no session check in key lookup (fails 1); the unconfined writer instead of the confined one (fails 2, including the junction test); an off-by-one in page conversion (fails 10); close without the unsaved check (fails 1).

## 4. A consequence found by the existing suite, and its fix

The new rule (undoing back to the saved content is clean) broke one existing engine test, `autosave_snapshots_only_changed_documents`, which asserted that undo is always "a change". Reading it showed a real hazard rather than an outdated assertion: the desktop writes a recovery copy for the edit, the user undoes back to the file's content, the document is now clean so no new snapshot is written, and **the stale copy of the undone edit stays in the recovery store**. A crash then offers to recover an edit the user had undone. (A clean quit already clears the store; a crash did not.) Fixed in two places, with a regression test each: `Session::take_obsolete_recovery()` reports, once, each document that was snapshotted and has since become clean, and the desktop's `autosave_now` withdraws those copies (`crates/ui-egui/src/recovery.rs`); the engine test now asserts no snapshot, one obsolete report, a new snapshot on redo and on a different edit, and no obsolete report while the copy is current; `undoing_back_to_the_saved_content_withdraws_the_recovery_copy` (UI, recovery suite) drives it through the app. Mutation: removing the withdrawal fails that test.

## 5. Not done, and not claimed

* **No adapter is on the service.** The service has no users but its tests and the parity test. "Private session ownership" is true of `Service`; the desktop's `Session`, the tools' `Session` and the MCP server's remain their own until BUILD-009. The acceptance "no service/automation dependency cycle" holds trivially (one dev-dependency edge, no cycle); "No UI dependency below L7" is the existing layer rule.
* **No authorization.** `RequestContext` carries a request id and nothing else; there is no actor, grant, policy, audit or release profile (BUILD-008). The capability and access fields of the descriptors are declarations, and nothing enforces them. Undo and redo are declared as needing the capability of the edit they revert (`document.edit.reverted`); who may revert what is BUILD-008's decision.
* **Path resolution against a root stays in `automation`.** The service's confined mode is stricter and smaller (root-relative, no `..`); absolute paths and `..` inside the root are refused by the service and accepted by the tools. Parity there is BUILD-009's, together with moving `resolve` somewhere shared.
* **Only these eight operations**, and only page rotation among edits. The rest of the catalogue, rendering through the facade, batches, resources and the UI control channel are not migrated.
* **`render_generation` is the engine's cache generation**, so it also moves for display-only changes; the late-result check uses the content revision, and a save that overlaps a display-only change is conservatively reported `edited_since` and left unsaved (engine `mark_saved_at` compares generations). Not fixed here.
* **No jobs, cancellation or deadlines** (`canceled`, `worker_failure` and `resource_limit` are declared codes; only the open size limit raises the last). The 512 MiB open cap is a stopgap, not a budget.
* **`unsupported_schema` is a thirteenth error code** beyond the twelve in the spec's list; recorded as a decision (a client must tell "update me" from "your request is wrong").
* The confined-link test and the rest of the service tests ran on Windows locally and on Ubuntu and FreeBSD hosted (the Unix path swaps a symlink); there is no macOS run. As in BUILD-006, on Unix the confinement check narrows the window to the instant before the replacement and does not close it.
* Codex review of `295722f0`: three P1 corrections requested and made; see section 7 and the [independent review](BUILD-007-codex-review.md). Not yet re-reviewed.

## 7. Review findings (2026-10-25): three P1 blockers, fixed

The [independent review](BUILD-007-codex-review.md) found three defects in the save and open paths. All three were real. Each is covered by a test written against the reviewer's failing case, and each fix was reverted once to see its test fail.

**R1 (P1): a late save could leave unsaved content marked clean, or restore an older destination.**

* *Marked clean.* The engine took the save's *generation* and, if the document had changed since, left the saved identity alone. So: edit E, a save of E starts, the user undoes E (back at the opened content, clean against the old file), the save lands (the file now holds E): the document showed the opened content, called itself clean, and closing it did not ask. **Fix:** a save is taken as a `SaveToken` (the generation **and** the identity of the content). When the document has moved on, the file is recorded as holding *the token's content*, so the document is unsaved exactly when it shows something else, and undoing or redoing back to what was written is clean (this also removes the conservative leftover recorded in section 1). Content identities continue across a `reload`, so an identity carried by a save in flight cannot equal one in the reloaded content. The desktop save path takes the same token: it had the same defect and has the same fix. *Tests:* engine `undoing_while_a_save_is_in_flight_does_not_leave_content_the_file_lacks_marked_clean` and `a_save_in_flight_across_a_reload_does_not_match_the_reloaded_content`; service `undoing_during_a_save_leaves_the_document_unsaved_because_the_file_holds_the_edit` (the file really holds the edit, a new session reads it back, closing without discard is refused, redo is clean). *Mutations:* leaving the old saved identity (fails 2 engine tests); restarting identities at reload (fails 1).
* *Older destination.* A save finishing late always set the document's path and name to its own destination, even when a later save (a different Save As) had already finished, which also aimed the next tracked save at the older file. **Fix:** each plan has a place in the order saves of its document were planned, and a plan that is overtaken writes its file and changes nothing else (`superseded` in its report): not the destination, not the saved content, not the tracked file version, with its real file effect still reported. *Test:* `a_save_that_was_overtaken_does_not_restore_its_older_destination` (the document keeps `b.pdf` and is clean against it, its version is unchanged, the next tracked save replaces `b.pdf` without a conflict and leaves `a.pdf` alone). *Mutation:* without the guard it fails.

**R2 (P1): a write receipt for document B could mark unwritten document A saved.** `finish_save(prepared, written)` accepted any receipt with any plan; the receipt was just a file version, so a content hash could not have told two saves apart. **Fix (the reviewer's preferred shape):** the completion is inseparable from its plan. `PreparedSave::write` returns a `WrittenSave` that contains the plan it came from, and `finish_save(&completion)` takes only that, so no caller can pair a plan with another write's result. A completion is refused, changing nothing, when its plan belongs to **another service** (plan numbers start alike in every service, so the number alone would not have been enough) or was **already finished or abandoned**, and the refusal still reports the file the write left on disk in `committed` (the write stands). Plans in flight are registered and bounded (`MAX_SAVES_IN_FLIGHT` = 16); `abandon_save` gives one up and a failed write does so by itself, so a dead worker cannot grow the table without limit. *Tests:* `a_write_completion_finishes_its_own_save_and_no_other` (two documents with byte-identical files and the same edit, deterministic clock; only B is written and finished, A stays unsaved, unwritten and cannot be closed without discarding; a completion finishes once and the refusal still names the file), `a_completion_from_another_service_is_refused_and_says_what_it_wrote` (the other service has its own plan with the same number in flight; it is untouched and still finishes its own, and the completion still finishes at home), `planned_saves_are_bounded_and_can_be_given_up`. *Mutations:* a foreign-service completion accepted (fails), a finished completion finishing again (fails), a refusal that hides the written file (fails 2), no cap (fails), a failed write that keeps its place (fails). *One test strengthened after a mutation survived:* the foreign-service check was first masked by the "already finished" refusal because the other service had no plan registered; it now has one.

**R3 (P1): a confined open followed a file symlink out of the root.** The folder was pinned and checked link-free, but the file name was opened normally. **First fix:** `pdfcraft_platform::file_identity::read_regular_with_version(path, limit)` opens the file without following a link and checks the handle it reads from: `O_NOFOLLOW` on Unix; on Windows `FILE_FLAG_OPEN_REPARSE_POINT` (opens a link itself). **The size limit is applied to that same handle** (`read_with_version_limited` and the strict reader), to the length the handle reports before anything is allocated and to the bytes actually read, so a file that grows is still stopped; a larger file is `resource_limit`, and `Service::with_open_limit` lowers the limit. The strict read is also used by the automation `doc_open` when a root is set. *Tests:* platform `a_strict_read_returns_a_regular_file_and_refuses_a_link_or_a_folder` and `a_read_stops_at_its_limit_on_the_handle_it_reads`; service `a_confined_open_does_not_follow_a_file_link_out_of_the_root` (the reviewer's case: a three-page document outside the root and `root/alias.pdf` linked to it; an ordinary file in the root still opens and an unconfined service still follows links) and `the_open_size_limit_refuses_a_large_file_as_a_resource_limit_and_opens_one_at_the_limit`. The two link tests make a real file symlink, which Windows allows with Developer Mode or an elevated user; on this machine it was available and they ran (no skip message); a machine without it prints `SKIPPED` and passes without testing the link half.

**R3 correction (2026-10-25, after the retest).** That first fix had a hole, which the retest found by source inspection: when the first handle reported a reparse point that is *not* a link (an online-only cloud placeholder, a deduplicated file), the reader opened the name a second time the ordinary way to read it, and a link substituted for the name in that instant was followed, outside the root. Documenting the exception was not enough. **The reopen is removed.** The reader now opens the name exactly once, and every decision is about that handle: only a regular file that is neither a link nor a reparse point is read (`strict_verdict`); a reparse point of any kind is refused with a message that says what it is and what to do. Nothing is ever read from a second open of the name. **The cost, stated:** a confined read on Windows now refuses a file that is only available online (OneDrive Files On-Demand and similar) or that sits on a deduplicated volume, with "a Windows reparse point (an online-only cloud file, a deduplicated file or a link of another kind) ... make the file available offline, or open it from outside the confined folder". "Confined" means the agent's `--root` and `Service::confined_to`; an ordinary open by the user in the desktop is not confined and is unchanged. The automation tools' confined `doc_open` takes the same refusal, where it used to read such a file after canonicalizing it. I judged fail-closed right for a security boundary and cheap to relax later if a use needs it (keeping a placeholder readable would need the same validated file bound to the read throughout, which std does not give without unsafe code); that is a product trade-off recorded here rather than decided for you.

*Tests for the correction:* `a_placeholder_is_refused_and_the_name_is_never_opened_a_second_time` runs the reader through a seam that lets the test play the first open and say "this handle is a reparse point": the first open hands out the real file's handle and then, as another program would, replaces the name with a link to a file outside the folder (a real link, where this machine can make one); the read must be refused **and the name must have been opened once**, which fails if any second open exists, link or no link. `a_strict_handle_is_read_only_when_it_is_a_plain_regular_file` pins the decision table, and `an_ordinary_file_is_read_from_the_one_handle_that_was_opened` shows an ordinary file is read from the single open. *Local results for this correction* (Windows 11 x64, `--offline --locked -j 2`): `cargo fmt --check` and `clippy -D warnings --all-targets` clean over the platform, service and automation crates; wasm32 check of platform and the service passes; `cargo test` over those three crates: **305 passed, 0 failed**, no `SKIPPED` line (the replacement test made a real file symlink). The engine, UI, app and CLI suites were not re-run: this change touches only the platform reader and its callers' behaviour for reparse points. *Mutations:* putting the old fallback back (reopen the name for a reparse point) fails the replacement test; letting the verdict pass a reparse point fails the table and the replacement test. A **real** cloud placeholder was not available and none was created; the placeholder is simulated at the seam, so the claim is "no second open of the name exists in the code and a test fails if one is added", not "a native placeholder was observed refused". (The review also noted that the first open keeps Rust's default share mode, so another process may replace the name while the handle is open. That cannot change what is read: the bytes come from the handle that was checked, whichever file the name later points to.)

*What these fixes do not claim.* A hard link inside the root to a file outside it cannot be told from the file and is not covered. The Unix branch of the strict read (`O_NOFOLLOW`, ELOOP and EMLINK) was not compiled or run locally; it is covered by the hosted Ubuntu and FreeBSD jobs once this head runs. A save that has been written for a plan that a later plan has since overtaken is still on disk (a write cannot be recalled once its worker has it); it is only refused its effect on the document, and says so. The review's final request, "reject a leaf swapped during open", is met by checking the handle that is read (there is no gap between looking and opening) and, after the correction above, with no exception.

**Local results for the corrected head** (Windows 11 x64, Rust 1.99.0, `--offline --locked -j 2`): `cargo fmt --check` and `clippy -D warnings --all-targets` clean over the service, engine, platform, automation and UI crates; wasm32 check of platform and the service passes; `cargo test` over the engine, platform, service, automation, UI, app, CLI and xtask crates: **1,900 passed, 0 failed** (engine 248 plus the earlier suites; service 26; platform 56 including the strict-read and limit tests; the 15 recovery tests; the scoped UI/app/CLI suite). No `SKIPPED` line was printed, so the file-symlink tests ran. `cargo xtask layers` OK.

This is the first run that compiled the Unix `O_NOFOLLOW` branch of the strict read, and it compiled and passed on Ubuntu and FreeBSD.
