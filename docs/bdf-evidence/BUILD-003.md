## 2. Slice 2: the four reusable workflows are replaced by workflows in this repository

**The gap slice 1 could not close.** Pinning the caller to a commit of `storytold/craft-common-actions` fixes which reusable workflow runs, but not the `uses:` lines *inside* it, which GitHub resolves when the job runs. Reading the four workflows and their composite actions at the pinned commit (copies in `craft-common-actions-43f4e83c/`; read as text) found **17 nested references to `storytold/craft-common-actions/actions/*@main`** (`release.yml` 13, `windows-arm64.yml` 1, `freebsd.yml` 1, `packaging-lint.yml` 1, one inside the `install-linux-deps` action). The acceptance "release execution cannot change through an unreviewed remote branch ref" cannot be met by pinning callers. Separately, the release workflow was triggered by any push to a `release` branch with `contents: write` and was handed the upstream-style Apple, Windows and Azure signing secrets.

**Decision (owner, 2026-10-16): build what is needed here; no licence is being requested.** `craft-common-actions` is public but has no licence file, so its code is not copied. The replacements are written for BDF from this repository's own scripts, the inputs recorded in our retained FreeBSD job log, and the public documentation of the tools used. Disclosure: before the decision I had read the whole upstream `windows-arm64.yml` (to diagnose the ARM64 failure) and the `uses:` lists of the others; the new files were written from the requirements, not by editing those texts, and their structure is the obvious one for the job (package, then install on ARM64).

## Corrections after the Codex review (R1 and R2, PR #2)

[Review](BUILD-003-codex-review.md), 2026-10-16: changes requested. R3 concerns the inventory (PR #3) and is recorded there. Local commands ran on Windows 11 x64 with Rust 1.99.0 and .NET SDK 7.0.102 (the hosted runners have newer SDKs). Raw logs are under `target/bdf-evidence/BUILD-003/`.

**R1 (P1): install only the package whose hash was verified (`b6e181c9`).** The old script verified the downloaded `wix.5.0.2.nupkg` and then ran `dotnet tool install ... --add-source <dir>`, which adds a feed to the ambient ones; NuGet queries feeds in parallel, so the executable that ran was not necessarily the verified bytes. Now the install uses `--configfile` with a config that clears every other source and names only the folder holding the verified file, a fresh global-packages folder and HTTP cache, and a fresh `--tool-path`; afterwards every file the verified package ships under `tools/` must exist in the installed tool folder with the same SHA-256 and the folder may hold no other file, or the install is refused; `wix` is run by its full path.

* **Red, with real bytes (not an argument-flow mock):** `test-install-wix.ps1` builds a poisoned `wix` 5.0.2 (the official package with its signature removed and a file added) and offers it from an ambient `nuget.config`. With the original shape (`--add-source`, no post-install check) the poisoned package was installed in **4 of 4 runs** and the test failed each time (`wix-mutation-addsource-run*.log`, `wix-mutation-summary.txt`).
* **Green:** the same test passes with the new script (`wix-test-run3.log`): a tampered package and a wrong recorded hash are refused and install nothing; the normal install passes and `wix --version` runs from the new tool folder; a control shows that a default install does consult the poisoned ambient source, and the script, run from the same directory, installs exactly the verified package with none of the poison. The test also runs in the package workflow before WiX is installed.
* **First hosted run of this correction failed, and the failure was my assumption (`e5d4dacb`).** The self-test failed in the package job and the ARM64 package job failed with it. On the runner's newer .NET SDK the `.nupkg.sha512` file that NuGet records for a correct install holds `nwM4/eb7...`, not the package's SHA-512, so my first post-install check (compare that record with the verified hash) refused a legitimate install; it failed closed, but it was a check on NuGet's metadata that I had validated only on SDK 7. It is replaced by a comparison that does not depend on the SDK: every file under `tools/` in the verified package is compared by SHA-256 with the installed copy, and the installed folder may hold no other file. The control was also changed: it had looked for the poisoned folder in the verbose log, whose wording differs between SDKs; it now checks that a default install, with the poisoned folder as the only ambient source, really installs the poisoned package. The poisoned package now also differs from the real one in `wix.dll`, not only by an added file.
* **Red and fail-closed, revised script** (`wix-mutation-summary-3.txt`): with the original `--add-source` shape and no post-install check the poisoned `wix.dll` is installed (2 of 2 more runs); with `--add-source` but the file comparison kept, the install is refused ("the installed tools/net6.0/any/wix.dll differs from the verified package; refusing"); the script as committed passes locally (SDK 7.0.102, `wix-test-run5.log`).
* **Limits:** the cache isolation uses `NUGET_PACKAGES` and `NUGET_HTTP_CACHE_PATH`; it is covered by the post-install hash check rather than proven separately. `wix` has no package dependencies (read from its nuspec), which is why a single local source suffices; a version with dependencies would need a source-mapped second feed.

**R2 (P2): parse YAML keys (`f1c87a0b`).** The scanner recognised only a line starting with the literal `uses:`. It now parses each file with the `yaml-rust2` crate and walks the mapping events, so quoted, spaced, flow, complex-key, escaped and next-line or block-scalar spellings are found, and `uses:` inside a `run` script or a string is not a reference. A value that is not a plain string (an alias, a mapping, a sequence) and a file that is not valid YAML are reported, not skipped; diagnostics keep the file and the line of the value.

* **Red:** five new tests failed against the line scanner, including Codex's fixture (twelve pinned references plus one floating quoted-key reference) (`red-r2-pins.log`). **Green:** 104 xtask tests pass; clippy `-D warnings`, fmt, layers, assets, pins, `cargo-deny` (advisories, bans, licenses, sources) and the 1.95 MSRV check pass. Three mutations (keys ignored, parse errors skipped, aliases skipped) are each caught (`mutations-pins-summary.txt`).
* **Found while correcting:** an older test used text that is not valid YAML (`run: echo uses: x@main`, a plain scalar containing a colon and a space); GitHub would reject such a file, and the parser did. The test is corrected.
* **New dependency (approved by the owner, 2026-10-16):** `yaml-rust2` 0.13.0 for `xtask` only. Provenance: crates.io, published by `davvid`, owners `Ethiraric` and `davvid`, MIT OR Apache-2.0, 65 million downloads, repository `Ethiraric/yaml-rust2`. The tarball (76,201 bytes) matched crates.io's recorded checksum before any build; it contains no build script, no `unsafe`, and no network or process use (its one environment read is a debug switch). It brings `arraydeque` 0.5.1 and `hashlink` 0.12.2 (both checksum-verified; both use `unsafe` internally, as data-structure crates do; `hashbrown` was already locked). Cargo also re-pointed five existing `windows-sys` lock edges when the dependency was added; that unrelated change was reverted by hand, so the lock diff is the three packages and `xtask`'s edge (26 lines).
* **Still true:** the scanner reads this repository's files only; it cannot see inside a pinned reusable workflow (none remains), and it does not check `run`-block downloads.

**Hosted validation of the corrections (draft PR #2).** First head `e5d4dacb`: packaging lint passed; the x64 package and ARM64 package failed as described above. Corrected head `f8bbf3c0`: **all five workflows pass**: [CI](https://github.com/btecme/bdf/actions/runs/38954319648) (fuzz skipped by its event condition, as before), [FreeBSD](https://github.com/btecme/bdf/actions/runs/38954319598), [Windows ARM64](https://github.com/btecme/bdf/actions/runs/38954319528), [Package (Windows x64, unsigned)](https://github.com/btecme/bdf/actions/runs/38954319523), which runs the isolation self-test on the hosted SDK before installing WiX, and [Packaging lint](https://github.com/btecme/bdf/actions/runs/38954319551). ## 4. Slice 3: the core capability inventory (deliverable 3)

Branch `chore/build-003-capability-inventory`, stacked on the PR #2 branch. The inventory is [bdf-capability-inventory.md](../bdf-capability-inventory.md) (readable) and `crates/automation/src/capability.rs` (data, decision API, tests).

**What it classifies.** Every one of the **163 automation tools**, the **219 command ids** (192 in the registry plus 27 that only the tool catalogue names, all planned or cloud), and **31 routes** (CLI subcommands, MCP methods and resources, UI control methods, operating-system entry points). Verdicts: Core (34 tools, 54 commands), Gated (2 tools: `command_run` and `command_batch`; 17 routes), Deferred (121 tools, 152 commands) and Excluded (6 tools, 13 commands). The core follows the PRD's CORE-01 to CORE-08 and CORE-10; the deferred list follows the PRD's "Deferred from v1" paragraph. CORE-09 (simple signature appearance, BUILD-016) and CORE-11 (diagnostics, BUILD-014, no tool or command exists) are recorded as gaps.

**Parameter modes.** For each core tool every parameter is either allowed or refused, and every enumerated parameter is split into core and excluded values (for example `comment_add.type`: eight annotation kinds are core, eleven are excluded; `doc_print.layout`: `fit` and `actual` are core, `poster`, `booklet`, `shrink`, `custom` and `multiple` are excluded; `doc_save.flatten_fill_sign`, `page_extract.delete` and `doc_split.bookmarks` are refused). The classification is mine, from the PRD text; widening any of it is a product decision.

**Default deny, and what is and is not enforced.** `check_tool_call(name, args)` and `check_command(id)` allow only Core: an unlisted tool, command, parameter or enumerated mode is denied, and `command_run` / `command_batch` are allowed only if every command they name is core. The completeness tests fail when a tool, command, catalogue command, core-tool parameter or enumerated mode exists that the inventory does not classify, when an entry is stale, and when a core tool automates a non-core command (or the reverse). **Nothing in the product calls the profile yet**: `pdfcraft-cli run`, MCP `tools/call`, compact `tool_call`, MCP resources, the control channel and the UI still reach everything; these are the inherited bypass routes the document lists, owned by BUILD-005 to BUILD-008. The parameters of the commands a dispatcher runs are not inspected.

**Evidence.** The ten tests in `capability::tests` pass (`capability-first-run.log`; the whole automation suite passes: 33 unit, 153 + 8 + 4 + 2 integration, `inv-automation-tests.log`); clippy `-D warnings`, fmt, layers, assets, pins, parity, wasm (31 crates) and the 1.95 MSRV check pass (`inv-*.log`). Eight mutations each make at least one test fail: a tool row removed, a command row removed, a command and its tool disagreeing, unknown tools allowed, refused parameters ignored, excluded modes allowed, a batch that only checks its first step, and a core parameter left unlisted (`mutation-*.log`, `mutations-summary*.txt`; the first removal attempt did not run because of a script error and was redone).

**Not done.** Enforcement (BUILD-007, BUILD-008); a machine check of the CLI subcommand list and the control-channel method list (the routes table is reviewed by hand and could drift); the parameters of commands; the web build and non-Windows behaviour (outside the desktop v1 scope); inventorying settings and file-association entries beyond the routes listed.

## Correction after the Codex review (R3, PR #3)

[Review](BUILD-003-codex-review.md): R3 (P2), `crates/automation/src/capability.rs`. `check_tool_call` judged an enumerated mode only when the argument was present and non-null, but a tool runs an omitted or null mode as its default. `doc_print` classified `comments_forms = "document-and-markups"` as excluded while its implementation defaults to exactly that value, so `{"doc":1,"path":"print.pdf"}` was allowed and the same call with the value spelled out was denied: two requests selecting one execution mode got different decisions.

* **Red, on the reviewed head** (`b9b5cc43`, in a throwaway worktree): a probe test comparing the omitted and the explicit form fails with "omitted: Allow; explicit: Deny(... is an excluded mode)" (`red-r3-reviewed-head.log`).
* **Fix.** An omitted or null mode is now judged as its default, like an explicit value (`EnumRule.default`). The defaults are constants in a new `crates/automation/src/defaults.rs` that the tools themselves read (`doc_print` subset, layout, orientation, comments_forms and duplex; `page_rotate` subset and orientation; `doc_combine` field_conflicts) and that the inventory names, so the mode a call runs in and the mode the profile judged cannot drift; the tools' behaviour is unchanged. A mode that is only read by an excluded layout (`order`, `binding`, `booklet_subset`) has no default: omitted selects nothing, and any explicit value is refused.
* **Product decision, made explicit:** the actual print default `document-and-markups` (print what is on screen, comments included) is now **core**; refusing it would deny every ordinary print. `document-and-stamps` and `form-fields-only` stay excluded. This widens the print surface by that one mode and is for the owner to confirm; it is the only classification change in the correction.
* **Tests** (14 in `capability::tests`, was 10): a synthetic tool whose default is an excluded mode denies the omitted, null and explicit forms alike, and says the default was the reason; every defaulted mode of every core tool is a core mode and decides the same omitted, null or explicit; a call that omits every mode is allowed for every core tool; the review's counterexample is allowed in all three forms; and a behavioural test runs the real `doc_print` and `page_rotate` and shows that omitted, null and the declared default give the same result and a different mode a different one (the markup default changes the printed bytes of a page that has a comment). Three mutations are caught: defaults ignored; the print default changed to an excluded mode; the tool reading its own literal instead of the shared constant (`mutations-r3-summary.txt`).
* **Checks:** fmt, clippy `-D warnings` and the whole automation suite (37 unit, 153 + 8 + 4 + 2 integration) pass.
* **Hosted result (draft PR #3):** on head `e79ad0d6` (the R3 correction with PR #2's R1 and R2 merged in) [CI passes](https://github.com/btecme/bdf/actions/runs/38956326692), fuzz skipped by its event condition. Only the main CI workflow runs for this change; the packaging, FreeBSD and ARM64 workflows are filtered by path and are not runs on this head. Observed through GitHub's API.
* **Still open, as disclosed:** nothing calls the profile at run time; command dispatch checks ids but not `params`, so `command_run(file.save, params.flatten_fill_sign=true)` is allowed while the equivalent direct tool call is denied (closure belongs to the enforcement work, BUILD-007 and BUILD-008); route completeness is hand-maintained.
