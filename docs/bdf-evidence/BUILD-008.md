## 1. Who is asking (`actors.rs`)

An `ActorContext` is human or agent, with the operating-system account, and for an agent the client name and the grant. **A caller cannot write one.** Its fields are private and it has two sources:

* `ActorContext::local_user()` takes **no arguments**: it reads the account the process runs as (`pdfcraft_platform::identity::current_user`: the Windows token's SID, or `uid:<n>` on Unix), so there is no name to claim. It is the person at the keyboard.
* `GrantStore::authenticate(client, secret)` turns a client's name and secret into an agent actor, after checking the secret against the stored grant. No JSON field, command-line argument or tool argument is ever read as an identity.

`local_user()` still means "act as the person", so *who may call it* is the question. A test (`tests/identity_gate.rs`) reads every production source in the workspace and fails if any crate other than the service calls it; the applications (`apps/`) are where the person's session starts, and tests may stand in for the person. A second test proves the scan is not blind. Mutation: adding such a call to the platform crate fails the first test.

## 2. What a client holds (`grants.rs`)

* **A new grant is read-only**: `document.read` on the open documents, no folders at all, eight hours. Anything more is asked for by name in the request. A grant is never open-ended (a minute to thirty days); capabilities are `document.read`, `document.edit.pages`, `document.save` and `document.close` (closing drops unsaved changes, so it is not part of reading), each limited to all open documents or a list of them; files are a separate permission: folders it may read from and folders it may write into, absolute, with no `..`.
* **Secrets.** 32 random bytes, shown once when the grant is issued (`bdfg_` and 64 hex digits) and never stored: the store keeps the SHA-256 and compares it in constant time, against every grant, so the time taken does not say which client names exist. Every failure to authenticate (no such client, wrong secret, revoked, expired, another account, a malformed name) is the same `AuthError`.
* **Storage.** A private file (a Windows access list that only the user, the system and administrators can use, read through `icacls /save` exactly as for the control token in BUILD-005; owner and mode 0600 on Unix), verified before it is read or written, at most 256 KiB and 64 grants. A file that is damaged, too big, of an unknown version, or readable by other accounts is an error and is **never silently replaced**; grants delegated by another account are dropped when loading, not honoured. A write that fails leaves the store as it was.
* **Revocation is shared.** A `GrantStore` is a cheap handle onto shared state, so a grant revoked through one handle (a command, a settings page) is seen at once by every service and every running operation that holds another. A revocation that cannot be written to disk still holds for the run.

## 3. What a request needs (`policy.rs`)

`Policy::decide` is the only place that says yes. A request is allowed when all of these hold, and refused with the first that does not (the stable reason is what the audit records):

1. **The release has the operation.** The descriptor must be `Core` in a core-only release; `Deferred` and `Excluded` are refused even for a fully granted client **and for the person**, and an operation with no descriptor at all (`decide_named`) is refused: what was not classified is denied.
2. **The actor is the person or holds a live grant**: it exists, is not revoked, has not expired, was delegated by this account.
3. **The grant holds the capability for this document.** An agent asking about a document it was not granted, one that does not exist and one of another session all get **the same answer** (`not_authorized`, `document_out_of_scope`); the person is told the truth (`not_found`).
4. **Undo and redo are not a way round 3.** The service keeps, for each document, the capability each undoable change needed (recorded when the change was made, in step with the engine's undo and redo), and an agent needs the capability of the change it would revert. A client that can only read cannot undo the person's edit; one that may edit pages can undo and redo a page edit; a step whose origin the history does not say is refused; a history that claims a step needed only `document.read` is refused (a read is never a change).
5. **A file needs a folder.** Opening needs a folder the grant may read from, saving one it may write into (for an in-place save, the document's own file counts), and a path containing `..` never qualifies.

The PDF's own permission bits are a further, independent intersection and stay with the engine, which enforces them when a change is applied; the service reports that refusal as `not_authorized` with reason `document_rights`, and the audit records it as a denial.

**Revocation stops queued and running work.** The actor is asked again immediately before an effect (an operation that changes, writes or closes), a save plan carries a watch that asks before anything is staged and again **at the moment the new bytes would replace the file** (a new `gate` on the platform's guarded and confined writes, asked before the folder revalidation and the version check), and the actor is asked once more before the result is handed back. A grant withdrawn while a request waited makes nothing happen; one withdrawn between the staging and the replacement writes nothing and leaves no staging file; one withdrawn after the write reports `not_authorized` listing the write that did happen (so the person's document is still brought into line with the disk: its next save is not a conflict) and hands nothing back.

## 4. What is recorded (`audit.rs`)

One record per outcome, refusals included: sequence, time, actor (human or client, with the client's name and the grant), operation, request number, the document's number in the session, content revision before and after, the outcome (`ok`, `denied` with the reason, `failed` with the error code), the effects outside memory (a file's **name** and size, or a closed document) and a warning count. **Never a document's content, a secret, or a full path** (tests assert none of the folder, the secret, `bdfg_`, a page's text or `%PDF` appears).

`FileAudit` keeps the log as JSON lines in a private folder, in segments of at most 256 KiB, at most eight (the oldest deleted when a new one starts: the log cannot fill the disk). Each line carries a short hash of the line before it and of itself; `verify` finds an edited line, a removed line (the sequence and link break) and a truncated one, and opening a damaged log keeps the damaged segment as it was, says so, and starts a new chain in a new segment. The chain is against accident, not an attacker: someone who can write the folder can rewrite all of it.

**A log that cannot be written stops the service serving clients** (`audit_unavailable`) until a working log is attached: a client's action that cannot be recorded does not happen. The person is not locked out of their own documents by a full disk. The one operation whose record failed has already happened; that one-record window is stated, not hidden.

**Document scripts are off unless someone has decided to trust them** (`ScriptTrust`, default `Disabled`; the service turns the engine's JavaScript off at construction and `with_script_trust(Enabled)` is the explicit decision). Granting a client access does not turn them on.

## 5a. The application part (second slice, stacked on the first)

**What was added.** Where the files live, the person's commands for them, and a gap in the first slice that the commands made real.

* **Where.** `pdfcraft_platform::state::access_dir()`: `%LOCALAPPDATA%\PdfCraft\Access` on Windows, `~/Library/Application Support/PdfCraft/Access` on macOS, `$XDG_DATA_HOME/pdfcraft/access` (or `~/.local/share/pdfcraft/access`) elsewhere. A value that is empty or not an absolute path is not used. The product folder name follows the applications' existing data folders (recovery and clipboard use `PdfCraft`) and is one constant, so the open product-name decision is one edit; the files inside carry no product name. `--state-dir DIR` overrides it (tests, portable use).
* **`pdfcraft-cli grant issue|list|revoke|prune`** and **`activity verify|show`.** `grant issue --client NAME` makes a grant that is **read-only unless `--allow` names more** (`document.edit.pages`, `document.save`, `document.close`; the reverted-edit pseudo-capability and anything unknown are refused), files need `--read DIR` / `--write DIR` (absolute, no `..`), and it expires (`--ttl 90m|8h|2d`, eight hours by default, a minute to thirty days). The client's secret is printed once, on stdout as part of one JSON object, with a notice on stderr; the grant file holds only its hash and `grant list` never shows it. These commands take no identity (an `--actor`, `--user`, `--as` or `--principal` option is "unknown option"): they run as the operating-system account running them. `activity verify` checks the audit chain and fails if it is damaged (a script can gate on it); `activity show --last N` prints the newest records as they are (the log holds no content, secrets or full paths).
* **A running service notices a revocation made from another process.** The first slice's shared revocation only worked inside one process, which is not the situation a person is in when they run `grant revoke` while an agent is connected. A `GrantStore` now remembers a stamp of the grant file (length and modification time; revoking flips `false` to `true`, so the length always changes) and re-reads it when it changes, before every check, authentication and listing. **If the file becomes unreadable (damaged, deleted, no longer private to the user) every grant fails until it is readable again, and the store does not write over it.** The test `revoking_from_the_command_reaches_a_service_already_running_in_another_process` runs the real binary to revoke while the test process holds a store it opened earlier.

**Tests.** Grants (unit): a revocation made through a second store on the same file is seen by the first without restarting it (and a grant issued by the second can be authenticated by the first); a damaged file fails closed, is not written over, and recovers when restored; a deleted file fails closed; a file that becomes readable by other accounts fails closed. CLI (through the binary, 7): a new grant is read-only and its secret is shown once and is in neither the file nor the listing; grants are listed, revoked (twice is fine), pruned, and an unknown id is an error; capabilities, folders and times are validated (15 refusals, each leaving stdout empty and the store untouched); the cross-process revocation above; a grant file other accounts can read is refused and left alone; the activity log verifies, shows the newest records without a path, and an edited record is reported with a failing exit; the commands are in the usage and no option names an identity. Platform: the state-folder rules for each platform's environment, in tests that run on that platform.

**Mutations (8 of the 9 failed a test):** the store never re-reading the file (3 tests); an unreadable file still letting `check` through (2); a store writing over a file it cannot read (1); `authenticate` ignoring an unreadable file (2); the stamp never changing (3); a new grant not read-only (2); unknown capabilities accepted (1); a damaged log verifying (1). The ninth (listing something extra) was a no-op of mine and proves nothing; it is not counted.

**Also found, and fixed.** A unit test of the time parser caught `--ttl -1h` being read as minus 3,600 seconds (the store's bounds would have refused it later, but the parser should not accept a sign): it now takes digits only. And the filled disk: a full-workspace `cargo test` filled the drive (54 GB of debug build output) and the linker failed with "insufficient disk space" (`LNK1201`, and `LNK1140` before it). It is the same hazard recorded in the project memory; the stale build generations were pruned (46 GB freed) and the tests re-run.

**Still not done, and said plainly.** The desktop application has no grants screen (the commands are the interface for now), nothing hands the secret to a client except the person copying it, and **no adapter is on the service**, so no client can reach a document through any shipped surface. The secret on stdout can end up in a terminal log or shell history; `--state-dir` and the stderr notice are the only mitigations here, and the delivery channel is the application slice that comes with the MCP adapter (BUILD-009).

## 6. Not done, and not claimed

* **The application part is only partly done** (section 5a): the command line issues, lists, revokes and prunes grants and verifies and shows the activity log, and the files have a default per-user place. The desktop has no grants screen, and nothing delivers a secret to a client. **Open decision for the owner:** the per-user folder is named `PdfCraft`, like the applications' other data folders, because the product name is undecided (BDF or PdfCraft); renaming it is one constant.
* **No adapter is on the service** (BUILD-009), so no MCP client, CLI script or UI control connection is subject to this policy yet. The automation tools' capability profile (BUILD-003) still enforces deferred modes of the *tools*; making the service's release profile and that one the same thing is BUILD-009's.
* **Same-user software.** Local capability policy is not a defence against software running as the user: it can read the user's files and call whatever the user can. It is a defence against other accounts (the private files), against a client doing more than it was granted, against mistakes, and (with the identity-gate test) against an adapter acting as the person by accident.
* **Where a secret travels.** This work makes the secret hard to guess and impossible to read back from disk; how it reaches the client (an environment variable, a config file the client owns, a pipe) is the application slice, and the choice matters.
* **Only four capabilities and eight operations,** the ones the service has. Forms, annotations, export, print and diagnostics capabilities arrive with their operations.
* **Revocation cannot undo what already happened**: an in-memory edit applied in the instant after the last check, before delivery, stands and is audited as a denial whose revision moved. The record is truthful about it.
* **The audit chain is not a signature** and its clock is the machine's.
* No Codex review yet. The Unix-specific code was not compiled locally; it compiled and ran in the hosted Ubuntu and FreeBSD jobs.
