## 1. F03: a save replaces only the version it may

**Before.** A headless `doc_save` wrote the session's bytes over its target without looking at what was there. Opening a file, changing it in another program and saving destroyed the newer version. The desktop has a file watcher, but a watcher is not a commit-time check (it can be late, and it only compares size and timestamps).

**Now** (`crates/platform/src/file_identity.rs`, new):

* **A version is its content**: SHA-256 and length. Timestamps are kept for display and never decide. Tests: the same length and the same modification time with different bytes is a conflict; the same bytes after a touch is not.
* **Three authorities** say what a save may replace, and there is no mode that replaces "whatever is there": `CreateNew` (the file must not exist), `ReplaceTracked` (the version this session last read or wrote) and `ReplaceConfirmed` (a version the caller inspected and names by its fingerprint).
* **The check runs inside the save**, after the new bytes are staged, flushed and closed and immediately before they replace the target (`persistence::Steps::guard`), not as a pre-flight followed by a long write. A test makes the file change while the bytes are being written and sees it.
* **Creating is atomic**: a new file is put in place with a hard link, which fails if the name is taken, never with a rename that replaces. A file that appears after the check refuses the save as a conflict; a filesystem without hard links falls back to the rename.
* **Both versions are kept.** A refused save writes nothing, leaves no staging file, and the session (or the app) still holds the edit.

**Headless** (`doc_save`, and `sign_document`, which rewrites the document's file and rebases the session; both go through one helper, `commit_document_file`): the session records the version of each document's file when it is opened (from the same handle as the bytes) and when it is saved. An in-place save replaces only that version; a save to another path creates it, and an existing file there is a conflict. A refusal says what is on disk and how to proceed: `disk_version` (a fingerprint) with the facts as JSON on the last line (`conflict`: `changed`, `exists` or `gone`), and a new `overwrite_version` parameter, accepting the fingerprint the agent inspected, or `"absent"` to recreate a deleted file. The tool description, schema and the capability inventory (`doc_save` is a core tool; `overwrite_version` is a core parameter) are updated together; the inventory's completeness tests pass.

**Desktop** (`save_doc_to`): in place, the authority is the version this session last read or wrote (the bytes it opened, or what it last wrote); to a file chosen in the system's save dialog (which already asks before replacing) it is the file that is there; otherwise nothing may be replaced. A conflict opens a **Save conflict** dialog: *Save a Copy…* (keeps the other version and saves elsewhere), *Overwrite* (bound to the version that was found: if the file changes again while the dialog is open that save is refused too and the dialog returns) or *Cancel*. The dialog uses the catalogue's existing words "Replace" and "Save as…" plus four new strings (a title and three messages).

Tests (all through the real surfaces): headless: a file changed after open is refused and both versions are kept, then saved elsewhere or replaced knowingly, with stale and malformed confirmations refused; same size and timestamp, different bytes; two sessions on one file, implicit and explicit path; a new path that exists, and a deleted file not silently recreated; the same refusal through `command_run` (`file.save`). Desktop (kittest): a changed file asks and keeps both versions, Cancel and Overwrite; the repeated change; a change that keeps size and timestamp; Save a Copy. Mutations, each reverted: the headless save back to an unconditional replace fails five tests; the desktop save without the version check fails four. The twelve UI test binaries that save documents pass (editing, commands, create, fill_sign, forms, pickers, prepare, print, compare, javascript, control, export), so nothing relied on silent overwrite; one existing test (`creating_images_with_dpi_through_tools`) saved three documents to one name and now uses one name each.

## 2. F06: root confinement while the tree changes

**Before.** `Automation::resolve` canonicalised a path and checked it was inside the root; later I/O opened the path. `doc_save` with no path reused the stored document path without resolving it again. A program with write access to the tree could replace a folder by a link (on Windows a junction, which needs no privilege) between the check and the open.

**Now** (`crates/platform/src/confinement.rs`, new, used for every write a tool call makes and for `doc_open`):

* **Windows: the destination folder is pinned.** It is opened and held without sharing for delete for the whole save. While that handle is open Windows refuses to rename or delete that folder or any folder above it, so none of the folders between the root and the destination can be replaced by a link. Missing folders are created one level at a time, each checked as made. A test shows the pin works: with a destination pinned, renaming it or its parent fails, and after the save ends it succeeds.
* **Every platform: revalidation at the commit.** Just before the bytes replace the target, the folder is canonicalised again and must still be the pinned folder with no link between it and the root. On Unix this is all there is.
* **Revalidation of implicit stored targets**: `doc_save` without a path resolves the stored path against the root again.
* **Central:** the confinement root is set for the duration of each tool call (a scoped thread-local), so every write the call makes, however deeply a tool nests, is confined; there is no per-tool list to forget.

Tests: a folder that is a link (junction on Windows, symlink elsewhere) is refused and nothing is created through it; missing folders are created inside the root and a folder outside is refused; **the race**: the folder is swapped for a link while the save is under way (from inside the write step): on Windows the swap itself fails and the save lands inside the root, elsewhere the swap succeeds and the commit check refuses the save, and in both nothing is written outside the root; and through the tools: after a document is opened from inside the root and its folder is replaced by a link out of it, the implicit save, an explicit save, a save into a new subfolder, a new file, `doc_split` into the link and a `doc_open` through it are all refused and a byte-identical decoy outside the root is untouched. The decoy is identical to the original so that the version check alone would not stop the save: without confinement the save writes through the junction (reproduced, `unwrap_err` on an `Ok`), with it the save is refused. Ordinary saves, including into new subfolders, still work.

## 3. Windows locking and handle strategy, and its assumptions

* **What it relies on.** A directory handle opened with `FILE_SHARE_READ | FILE_SHARE_WRITE` and not `FILE_SHARE_DELETE` blocks rename and delete of that directory and of every directory above it (observed: the pin test). The target file is replaced with `ReplaceFile`, which fails if another process holds the target open without sharing; the staging file is exclusive while written.
* **Assumptions.** The root and the folders above it are trusted: they were chosen by the user, and a swap above the root is not defended. The attacker cannot cause the operating system to ignore sharing modes (a kernel-level or backup-privilege actor can). The attacker does not hold the destination open in a way that denies the pin; if so the save fails closed.
* **What it does not claim.** Canonicalising a path and then opening it is not enough, and this work does not rely on it: it is the first of three layers (check, pin, commit-time revalidation). The reads other than `doc_open` (images, fonts, certificates, attached files) are still path-based and not pinned.

**First hosted run (`02c80c0b`) found three defects of mine, all fixed.** (1) Linux clippy: `std::fs::File` was imported for Windows-only code in `confinement.rs`. (2) Windows and, by the same suite, FreeBSD: the language-coverage tests (`*_covers_ui_literals`) fail for sixteen languages when a new `tl!` string has no translation, and my first dialog added seven. The dialog now reuses the existing "Replace" and "Save as…" entries and has four new strings, translated into those sixteen languages (Arabic, Bulgarian, Czech, German, French, Hungarian, Italian, Japanese, Kazakh, Lithuanian, Brazilian Portuguese, Russian, Slovene, Turkish, Ukrainian, Simplified Chinese). **These translations were written by Claude, following each catalogue's existing terminology and quoting, and have not been reviewed by native speakers**; they should be reviewed like any other contribution. Spanish, Polish, Greek, Telugu and Traditional Chinese have no coverage test and fall back to English for these four strings. The FreeBSD log would not open in the browser pane; its failure is attributed to the same coverage tests because it runs the same suite, which the corrected head will show.

**Third and fourth hosted runs.** The attribution hashes of the sixteen edited catalogues (tracked assets) also had to be updated, which my scoped local runs had not covered. ## 5. Not done, and not claimed

* **Unix confinement is not race-resistant.** There is no pin; the commit-time check narrows the window to the instant between it and the rename. Handle-relative I/O (`openat`) would close it; no safe wrapper is in the approved dependency set. **The work item's stop condition applies on Unix: `--root` is a guard against mistakes and ordinary traversal, not against a program that can modify the tree, and agent write access should stay gated there.** BDF ships for Windows first.
* **No hostile second account** was used; the swaps are made by the test process itself, which has the same rights as an attacker with write access to the tree.
* **Conflict authority covers document saves** (`doc_save`, `sign_document`, and the desktop save). The other file-producing tools (split, extract, combine, export, OCR, measurement exports, printing) still replace an existing output by name; they are confined, but they do not check the version of the file they replace. This is the inventory of what remains, not a claim that it is covered.
* **A recovered document** (opened from an autosave) has no read version of its file; its first in-place save asks, through the conflict dialog, before replacing.
* **A save in the instant between the check and the replacement** is not seen (`ReplaceFile` refuses a target another process has open without sharing, which covers the common case).
* **The desktop file watcher is unchanged**; the commit-time check is independent of it.
