## 1. The finding and what was found beyond it

F02: the headless save (`crates/automation/src/lib.rs`) wrote the staging file and renamed it without flushing, while the desktop save flushed. Reading both paths and the callers turned up more, all in the same area:

| # | What | Where (before) |

| 1 | Headless save never called `sync_all`; a failed flush could not fail the save. | `automation::write_atomic` |
| 2 | Two copies of the staging-write-rename routine (desktop, headless) with different guarantees. | `ui-egui::editing::write_atomically`, `automation::write_atomic` |
| 3 | **A rename replaces a restricted file's access list.** On Windows `std::fs::rename` (MoveFileEx) gives the new file the folder's inherited access list. ## 2. The service

`crates/platform/src/persistence.rs` (new), documented at the top of the file:

* `write_replace(path, bytes, form)` / `write_replace_with(.., suffixes, &Steps)`: inspect the target (a folder or a device is refused), create a private staging file with an unpredictable name (`create_new`, as before; now `0600` on Unix and opened with no sharing on Windows), write, **flush** (`sync_all`; macOS falls back to `fsync` where the volume refuses a full flush, as the desktop already did), then replace. Every failure before the replacement removes the staging file and leaves the target untouched; the error says which step failed (`Stage::{Inspect, Stage, Write, Flush, Replace}`).
* **Replacement.** Unix: the existing file's mode is copied to the staging file (a new file gets the mode an ordinary new file gets in that folder, read from a probe file because the umask cannot be read without changing it), then rename, then the folder is flushed (`Committed::directory_flushed`). Windows: `ReplaceFile` through `winsafe` (already a workspace dependency; no new crate, no `unsafe`), with a backup name; if it fails part way and the target is gone, the original is renamed back, and if that fails too the error carries `original_copy`, the file that holds it. A new file or a symbolic link (the link itself is replaced, so a save cannot be redirected) is a plain rename.
* `write_output(path, bytes, form)` for command-line outputs: the same, but a symbolic link is followed (the file behind it is replaced and the link stays) and something that is neither file nor folder (`/dev/stdout`, a pipe) is written in place.
* `Steps` lets a test make the write, the flush or the replacement fail. `Steps::real()` is the only set the product uses.

**Callers.** Desktop `write_atomically` and headless `write_atomic` are now thin wrappers (same names, same signatures, same staging-name shapes, so the planted-name tests of both stay as they were); `Automation::write_output` and the seven `--out` writes of `pdfcraft-cli` use `write_output`. Dependency changes: `pdfcraft-platform` gains `winsafe` (Windows) and `rustix` (macOS, moved from `pdfcraft-ui-egui`, whose only use it was); `pdfcraft-cli` gains `pdfcraft-platform`; `Cargo.lock` changes by those edges only.

## 3. Save state

* `Session::mark_saved_at(id, bytes, path, generation)` and `Saved::{Rebased, EditedSince}` (new). The document always takes the new path once the file is written. If it was edited since the bytes were taken (`edit_generation` differs) nothing else is touched and `EditedSince` is returned; otherwise editing is rebased and the document is clean. If the saved bytes cannot be reopened it is `EditError::Reopen`, with the document unsaved and holding its own state. `mark_saved` keeps its signature and calls it with the current generation.
* Desktop `save_doc_to` takes the generation with the bytes. A failed write: "Couldn't save", the document unsaved, recovery data and original file untouched (it never reached `forget_recovery`). A committed save whose reopen failed: the existing, already translated notice "Saved, but reopening failed: {e}", now with the document pointing at the file that was written, recovery retained, no "after" action (a pending close does not proceed). `EditedSince`: a new notice, "Saved {name}, but changes made while saving are not saved yet", unsaved, recovery retained. The new notice has no translation in the 22 catalogues yet (untranslated labels use English).

## 5. Not done, and not claimed

* **Windows staging privacy: superseded.** This section first reported the staging file as readable through the folder's inherited list between close and replace, because `winsafe` has no access-list setter. The Codex review was right that reporting did not meet the acceptance criterion; section 6 replaces it with a design that gives the staging file the target's list before any byte is written. Remaining limit: no second-account test.
* **Unix and macOS are not exercised locally** (Ubuntu ran them hosted for `67693735`; macOS has not run). The mode copy, the umask probe, the folder flush, the `0600` staging file, the symbolic-link behaviour and the macOS `fsync` fallback are covered by tests that only a Linux or macOS run executes.
* **No power-interruption experiment.** `sync_all` and the folder flush are requested; whether a volume honours them was not tested.
* The owner is not preserved on Unix; `ReplaceFile` on Windows takes the Windows long-path and non-Unicode limits of `winsafe` (a name that is not valid Unicode is refused with a message rather than saved without its permissions).
* The `EditedSince` path and the reopen-failure path are tested in the engine; the UI's handling of them is not exercised by a UI test (the synchronous save cannot reach `EditedSince`, and no fixture makes the written bytes unreadable).
* Other writers were not changed: settings and recovery metadata already use `write_atomically`; the control-channel file, the log file and the PKCS#12 export (which has its own flush) were left alone.

## 6. Corrections after the Codex review (R1 and R2)

[Review](BUILD-004-codex-review.md) of PR #5 at `0d1a64f2` and `67693735`: two P1 findings, both reproduced independently. Status of each below; "hosted" is stated only where a run was observed.

**R1: staged bytes were readable through the folder's inherited access list.** Correct: the old text of section 5 called a millisecond exposure acceptable, and a crash would leave the file behind. Reporting the stop condition did not meet the acceptance criterion, so the design changed.

* **Design (no new dependency, no `unsafe`).** `ReplaceFile` gives the file it moves into place the access list of the file it replaces, and it does so for a hard link of the target. So on Windows an empty staging file now replaces a hard link of the target (`target.acl`, one file with the target's access list); the staging file leaves that step carrying the target's list **before any byte is written**, and is then opened for writing under that name. Observed first with `icacls` on a scratch folder (target: user only plus an explicit Users-read entry; the empty staging file inherited the folder's broader list; after replacing the link it had the target's two entries; the target was untouched). A plain copy does not carry the list (also observed), which rules out the simpler design.
* **Where it cannot be set up the save is refused before a byte is written**, with the target, the folder and the error kind unchanged: no hard links on a volume that keeps access lists, an unknown volume, a failed hand-over (this includes a read-only target, which `ReplaceFile` refuses at that first step). A volume with no access lists at all (FAT, exFAT) cannot make hard links and has nothing to keep private, so the save goes ahead there; a refusal would stop saving to a USB stick. Names made along the way (`.acl`, `.acl.bak`) are removed on every path, the target never.
* **Adversarial checks at every boundary** (`staged_bytes_are_never_more_readable_than_the_target_at_any_stage`): the folder grants more than the target's own list, and the staging file's access list is read and compared with the target's before the first byte is written, after the bytes are written, at the flush, with the handle closed just before the replacement, and at the injected failure (where a crash would leave the file behind); then the same save with nothing injected. A second test shows a plainly created staging file does take the folder's list, so the first cannot pass by accident. Refusal tests: no link on an access-list volume, unknown volume, hand-over failure, each refused with no byte written and no leftover; FAT-like volume saves; the real volume check reports access lists on the test volume.
* **Limit of the evidence.** The observer is the access list itself, not a second Windows account reading the file: none was provisioned (the review's probe used a restricted token at a service seam). Equality of the staged and target lists is the property that matters, but it is not the same experiment.

**R2: a failed refresh published the new state and cleared `dirty`.** Correct, and in a method this work had changed.

* `Session::mark_saved_at` now prepares the rebase beside the working state and publishes it only if the whole refresh succeeds. The saved bytes are opened as a candidate; it is swapped in only to refresh the view; if that fails the working document is put back (edits, undo and redo, XFA layout, view) and the renderer rebuilt. The destination path is adopted either way, because the file is on disk. On a failure the document is marked **unsaved even if it was clean** and its generation moves on, so close asks and autosave writes a recovery copy.
* Engine cases, both red on the previous code and green now: valid structure that cannot be shown (`a_saved_file_that_reads_but_cannot_be_shown_leaves_the_working_edit_alone`: the working Title edit, the undo step and the destination survive) and a clean document with bytes that cannot be reopened (`a_clean_document_whose_saved_copy_cannot_be_reopened_becomes_unsaved`, run for unreadable bytes and for the unshowable tree).
* UI: `PdfCraftApp::record_committed_save` now holds the post-write recording (the filesystem commit and the refresh outcome stay separate, as asked). `crates/ui-egui/tests/recovery.rs` drives it: for both bad-bytes kinds the notice says "Saved, but reopening failed", the document is unsaved with its edit, points at the file written, the recovery copy is kept and closing still asks; a clean document becomes unsaved and autosave then writes recovery; an edit made while the save was in flight is kept, unsaved and recoverable with its own notice. The two reopen cases fail against the previous engine and pass now; the in-flight case passes on both (that outcome existed) and guards it.

**Second R2 finding: the working and display buffers (retest of `c1d7b67e`).** [Retest](BUILD-004-codex-retest.md) closed R1 and reopened R2: correct, and a real defect of my correction. `refresh` begins by releasing the editor's *current* document into `doc.bytes` and `doc.display`; during my validation swap that document is the rejected candidate, so after a failed rebase I had restored the model but left both buffers holding the rejected file. The renderer was rebuilt from it (0x0, "page 1 does not exist") and `autosave_snapshots` reads `doc.bytes`, so the next autosave wrote an unreadable file over the last good recovery copy. My first tests counted recovery files and checked `info.pages`, which cannot see that.

* **Fix.** `mark_saved_at` captures `doc.bytes`, `doc.display` and the XFA report before the swap and puts all three back with the model on failure, then rebuilds the renderer from the restored display. Nothing else about the correction changes (destination adopted, unsaved even if clean, generation moved so autosave writes again).
* **Tests, red on the state Codex reproduced** (removing just the two restore lines fails both): the engine now checks that after a rejected rebase `bytes` and `display` equal their values before, the page still renders at its size, and the **next autosave snapshot reopens in a fresh session with the edit** (the snapshot before the failure is also checked); the clean-document case checks its recovery copy is its own content for unreadable bytes and for the unshowable tree. The UI recovery tests now write the next autosave through the real `RecoveryStore`, read the stored bytes back, open them in a new session and check the delete is in them (two bad-bytes kinds, dirty and clean documents).

**Hosted failures of the first runs.** `67693735` (the mode and ACL-fixture corrections) is **green on Windows, Ubuntu, wasm and ARM64** as observed through the API; FreeBSD was still running when this was written, so it is not counted. The Ubuntu run is the first execution of the Unix code: the mode test that failed at `0d1a64f2` passes. The dependency job fails on three inherited advisories: `zvariant`, `zbus_names` and `zvariant_derive` (RUSTSEC-2026-0370, -0371, -0372, published 2026-10-16, informational "unmaintained", no patched version; the remedy is a move to zbus 6). Disposition: **three entries in `deny.toml`, one per advisory, each with its reason and the revisit condition** (accesskit and atspi on zbus 6, then move the platform crate and delete the entries). Not a blanket ignore: with the entries removed the gate fails on exactly those three crates (reproduced), with them it passes (`advisories ok, bans ok, licenses ok, sources ok`), and any other advisory still fails it.
